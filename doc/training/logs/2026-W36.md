# Learning Log - 2026-W36

## 2026-08-31 - Issue #6 backend foundation design

### Decisions and reasoning

- Chose `uv` for the independently buildable Python project under `apps/api/`, with
  `pyproject.toml`, a committed lockfile, and separate runtime and development dependencies.
- Chose to let the API start during a temporary PostgreSQL outage. Liveness remains independent of
  the database, while database-aware readiness returns a safe `503` until PostgreSQL recovers.
- Defined a minimal health response contract that reports database availability without returning
  exception text or connection details.
- Chose typed settings for environment, logging, the database URL, and the readiness connection
  timeout. Local defaults use disposable Compose-only credentials; production must override the
  database URL.
- Distinguished invalid configuration, which fails startup, from temporary database unavailability,
  which leaves the process live but not ready.
- Chose FastAPI lifespan startup and shutdown for database engine construction and disposal.
- Selected the minimal runtime set: FastAPI, Pydantic, pydantic-settings, SQLAlchemy, Psycopg 3 with
  its binary extra, and Uvicorn with standard extras.
- Selected pytest, HTTPX, and Ruff as development dependencies. Deferred Alembic, async test
  plugins, coverage tooling, and Testcontainers because Issue #6 does not yet require them.
- Chose synchronous SQLAlchemy for the initial service. It keeps connection lifecycle and endpoint
  tests small while synchronous FastAPI route functions avoid blocking the event loop.
- Chose a minimal `apps/api/app` package with separate configuration, database, health, and
  application-factory modules. Deferred empty domain-oriented packages until later features require
  them.
- Separated fast unit tests from PostgreSQL integration tests so their dependency and execution
  contracts remain explicit.
- Kept `compose.yaml` at the repository root for shared local infrastructure and API-specific
  environment examples, package metadata, lockfile, and commands inside `apps/api/`.
- Chose an application factory and Uvicorn `--factory` target to avoid settings and database resource
  construction as module-import side effects.

### Verification status

- These are design decisions only. No FastAPI application, Compose service, automated test, or
  successful backend command exists yet.

## 2026-09-02 - Issue #8 domain-schema design checkpoint

### Decisions and reasoning

- Treated every `learning_cards` row as confirmed content with required nonblank term and meaning;
  future incomplete AI content remains in separate draft tables outside this ticket.
- Made a card's deck required and derived its languages through that deck instead of duplicating
  language columns on cards. Optional reading, pronunciation, and romanization stay in the shared
  multilingual card model.
- Selected `review_states.card_id` as the primary key because the identity of a current state is its
  card; an unrelated review-state ID would add no value.
- Distinguished `NOT NULL` from value checks. Current review state constrains stage, ease, interval,
  version, required next-review time, and the ordering of present last/next review times.
- Reconfirmed one embedded example with no independent lifecycle. A child table and JSON storage
  were rejected; multiple examples later require a migration and API change.
- Defined tags as normalized per-owner resources. The association stores owner ID and uses composite
  owned foreign keys so separately valid card and tag IDs cannot cross user boundaries.
- Kept retry identity on the atomic review batch and retained before/after scheduling values,
  authoritative time, and algorithm version on immutable review events.
- Refined indexes around four named access patterns: active cards in a deck, decks by language,
  due-review retrieval, and owner review history. Deferred speculative substring-search indexing.

### Corrections and learning

- Corrected the initial suggestion that `learning_cards.deck_id` could be nullable; a confirmed card
  must belong to a deck.
- Corrected the assumption that independently valid owner and resource foreign keys enforce shared
  ownership; composite foreign keys to unique owned keys provide that guarantee.
- Corrected the idea that required scheduling columns alone reject invalid values; `NOT NULL` and
  range/cross-column `CHECK` constraints protect different invariants.
- Corrected the review-history index field from current-state `last_reviewed_at` to event
  `reviewed_at` and added stable ID tie-breakers to ordered indexes.

### Verification status

- Design discussion is recorded in `doc/training/issues/issue-8/`.
- No Issue #8 migration, model, fixture, constraint test, ER diagram, or PostgreSQL query-plan result
  exists yet, so no implementation evidence was added to the evidence ledger.
