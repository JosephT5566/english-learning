## 2026-08-29 - Issue #5 authorization response design

### Decision and reasoning

- Chose a non-disclosing `404 Not Found` for both nonexistent resources and resources owned by
  another user so the API does not confirm that another user's resource exists.
- Reserved `403 Forbidden` for a resource that is intentionally visible to the authenticated user
  but for which a particular operation is prohibited, such as a possible future read-only shared
  deck.
- Kept `401 Unauthorized` for missing or invalid authentication and `409 Conflict` for an owned
  resource whose current state prevents the operation.
- This response policy does not replace backend authorization; every resource query must still
  enforce the authenticated ownership boundary.

## 2026-08-29 - Issue #5 review batch atomicity

### Decision and reasoning

- Chose all-or-nothing review batches. Every item is validated and all review events plus current
  states commit in one transaction.
- Any invalid, inaccessible, archived, stale, or conflicting item rolls back the complete batch;

  partial-result reconciliation.

## 2026-08-29 - Issue #5 review idempotency and concurrency

### Decision and reasoning

- Required a client-generated UUID in `Idempotency-Key` for each logical review batch. The browser
  persists and reuses the key with the exact request body after ambiguous transport failures.
- Added a durable `review_batches` concept scoped by `UNIQUE (owner_id, idempotency_key)`, with a
  canonical request hash, authoritative review time, algorithm version, and item count.
- Bound review events to their batch and prohibited more than one event for the same card in one
  batch.
- Defined one transaction that inserts the batch, locks card states in deterministic order,
  validates ownership/active state/expected versions, calculates transitions, inserts events, and
  updates current states before committing everything together.
- A same-key/same-hash retry replays the committed result; same key with different content returns
  `409 idempotency_key_reused`.
- A pre-commit failure leaves no durable batch or review change. A lost post-commit response is
  recovered by reading the committed batch and events.
- Each item carries `expected_version`. For concurrent different-key batches, the first valid commit
  advances the version and a stale contender rolls back completely with a conflict.
- Successful batch records are retained with review history; failed validation attempts are not
  stored as completed batches.
