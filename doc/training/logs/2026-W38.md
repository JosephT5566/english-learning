# 2026-W38

## Issue #26 — protected production schema upgrades

- The operator reported an initial Cloud Run deployment, local Alembic upgrade against Neon, and a
  `pg_dump`/`pg_restore` data transfer. The deployed API returned
  `{"status":"ready","checks":{"database":"ok"}}`, confirming the reported runtime database probe;
  authenticated behavior and restored-data reconciliation remain unverified from repository
  evidence.
- Added a manual production migration workflow that uses GitHub OIDC instead of a service-account
  key, keeps the Neon URL in GCP Secret Manager, serializes runs, requires an existing immutable
  commit-tagged image and explicit confirmation, and invokes a one-task zero-retry Cloud Run job.
- A separate Cloud Run execution runs `alembic current --check-heads` after upgrade, followed by the
  deployed API's database-readiness check through its runtime role. Data restore, downgrade,
  application deployment, and traffic promotion remain deliberately separate.
- Artifact Registry `asia-east1` and Cloud Run `asia-southeast1` are now independent release
  settings. Remote workflow execution, live authorization checks, data reconciliation, and rollback
  rehearsal remain pending.

## Issue #26 — protected API image publishing

- Added a separate manual image-publishing workflow that authenticates through WIF, requires an
  explicit confirmation and protected environment, refuses to overwrite commit tags, builds the API
  for `linux/amd64`, pushes to Artifact Registry, and verifies the result.
- The publisher uses a dedicated Artifact-Registry-Writer identity and cannot manage Cloud Run,
  impersonate the migration job identity, or read database secrets. Migration and deployment remain
  separate operations; remote workflow execution is not yet verified.
