# Issue #38 學習筆記：從單字卡到安全的語意檢索設計

這份筆記解釋 #38 為什麼這樣設計、我們實際驗證了什麼，以及哪些事情還沒做。#38 是**檢索設計與評估**階段：目前沒有上線的語意搜尋 API、`card_embeddings` 資料表或 LLM 回答功能。完整契約與 SQL 見 [Issue #38 設計](README.md)。

## Chapter 1. 我們要解決的問題

現有單字卡可以依牌組、語言、狀態等欄位查詢，但使用者可能想搜尋「描述工作後精疲力盡的字」。卡片裡可能寫的是 `burnout` 或 `exhausted`，查詢與卡片不一定有相同字詞。語意檢索會把查詢與卡片文字各轉為向量，再比較它們的接近程度。

這一階段只回答「哪些**自己的單字卡**最相關」，不生成教學回答。嚴格來說，這是未來 RAG 所需的 retrieval 部分，尚不是完整的 RAG。若要問「今天到期幾張」或「某牌組有多少卡」，資料庫已有精確欄位，應直接用 SQL，不需要 embedding。

## Chapter 2. 資料如何流動

```text
已確認卡片建立／語意欄位編輯
  -> 組成固定格式的語意文字
  -> Vertex AI RETRIEVAL_DOCUMENT -> 512 維向量
  -> 依卡片、owner、模型版本保存衍生資料（#39 實作）

使用者輸入自然語言查詢
  -> FastAPI 驗證 Google 身分，取得內部 owner_id
  -> Vertex AI RETRIEVAL_QUERY -> 512 維向量
  -> PostgreSQL 先限制 owner／有效卡片／語言／牌組／目前版本
  -> 算 cosine distance，排序並回傳最多 K 張卡（#40 實作）
```

同一模型的「文件」和「查詢」要使用對應的 task type。向量本身不會證明卡片屬於誰，也不能替代後端授權；它只提供相似度。選用 Vertex AI `gemini-embedding-001` 的 512 維輸出，是 #39 的設計基準。Google Cloud IAM 可讓既有 Cloud Run 服務身分呼叫服務，但正式服務身分的權限與實際請求路徑尚未驗證。卡片與查詢文字會送到供應商；目前只送過合成資料。

## Chapter 3. 為什麼向量與卡片分開存

`learning_cards` 是使用者已確認的學習資料；embedding 是可以重新計算的衍生資料。我們選擇另建 `card_embeddings`，以 `(card_id, owner_id, model_version)` 識別向量，並用複合外鍵維持卡片與向量的 owner 一致。這讓模型升級時可以並存新舊向量，也能在結果不理想時回切舊版本。

每個向量還要記錄 canonical text 的 `content_hash`。搜尋只使用「模型版本正確，且 hash 與目前已確認卡片相符」的向量。假設卡片從 *tired* 改成 *excited*，舊向量即使仍在資料庫，也不能拿來代表新內容。缺少向量或 hash 不符時，卡片仍可正常複習，只是暫時不出現在語意搜尋結果。

canonical text 只包含詞、意思、詞性、讀音、例句、同反義詞等語意欄位，並固定順序、正規化與 hash 方式。學習進度、時間戳、ID、owner、牌組標題、來源註記等不放進 embedding 文字。**修改語意欄位才需要重算向量**；複習排程改變不用。封存卡片或牌組也不用呼叫 provider，搜尋 SQL 會立刻排除它們。既有確認匯入與未來 AI 草稿確認都必須進入同一個「已確認卡片後補向量」流程；草稿不直接成為可搜尋的學習卡。

## Chapter 4. API 失敗時，卡片會怎樣

建立或編輯卡片的資料庫交易先完成，再呼叫 embedding API。若 API 逾時、限流或回傳無效向量，**卡片寫入仍成功**；衍生向量標為缺少／待重試。操作人員可用有限批次的 backfill 補齊，不需要先引入 queue。這種分離也避免外部 API 請求長時間占住卡片交易。

還有一個競態：第一次編輯的 embedding 請求尚未回來，使用者又完成第二次編輯。回寫向量時必須再核對卡片目前的 owner 與內容 hash；若已變更，就丟棄過期結果。重試次數、每次批量與執行時間都要有上限，否則外部服務故障可能造成無限工作量。這些規則目前是設計，實作與交易測試屬於 #39。

## Chapter 5. Owner 安全與 Top-K 的順序

最重要的邊界是：**先找有權且符合條件的候選卡，再從其中選 Top-K**。查詢的 `owner_id` 由 FastAPI 驗證身份後取得，不接受瀏覽器提供。卡片、牌組、向量都以相同 owner 連結；SQL 同時限制有效狀態、語言、可選牌組、目前模型版本和內容 hash。跨 owner 的卡片在排序前就不屬於候選集合，不可能因相似度高而被回傳。

`<=>` 是 pgvector 的 cosine distance，**越小越接近**。若 API 回傳 `score = 1 - distance`，那是 cosine similarity，**越大越接近**，不是「有 90% 機率正確」。我們目前沒有能支持固定分數門檻的資料。搜尋預設最多 10 筆、硬上限 20 筆；部分卡片尚未建立向量時，可以回傳少於 K 筆，並標示索引覆蓋狀態。

## Chapter 6. 為什麼現在不加 HNSW

HNSW 是向量近鄰的**近似索引**：資料量大時可能加速查詢，但會增加維護成本，也可能漏掉真正最近的卡。尤其當多人向量共用索引時，近似搜尋先找到的候選可能大多屬於其他 owner；之後套用 owner 篩選，剩下的結果可能不足。這是搜尋品質問題，雖然 SQL 授權條件仍不能被省略。

操作者在 Neon 回報目前有 597 張有效卡與 2 個 deck，測試 branch 上可啟用 pgvector 0.8.6。用 597 筆**合成向量**執行一次 `EXPLAIN`：資料庫使用 owner／deck／language 的 bitmap index，取得 90 筆候選，再用記憶體 top-N sort 回傳 10 筆；該次執行為 0.434 ms。這支持 MVP 先用精確的篩選後排序。它不是正式三表查詢或 p95 延遲；#39 建表後要重跑最終 SQL 的計畫，資料增長或延遲真的成為問題時才重評 HNSW。

## Chapter 7. 我們怎麼衡量「找得好不好」

[合成標記集](relevance.json)有 10 張虛構卡、7 個英文查詢。每個查詢把相關卡標為 2（強相關）、1（相關）或 0（不相關）。`nDCG@5` 同時看「有沒有找對」與「相關卡排得夠不夠前面」；grade-2 `Recall@5` 看強相關卡在前五名找回多少。先定義資料與指標，再跑模型，避免看完結果才改成功標準。

[離線評分工具](evaluate.py)的字面詞重疊基線得到 macro nDCG@5 **0.5655**、強相關 Recall@5 **0.6429**。操作者手動執行 [Vertex AI 評估工具](evaluate_vertex.py)，用 10 張合成卡與 7 個查詢發出 17 次請求，回報兩個指標都是 **1.0**，共 314 input tokens。Cloud Shell 到 Vertex AI 的單次請求延遲 p50／p95 為 **1200.7／1296.3 ms**。這是小而簡單的合成集，不能推論真實使用者的相關性，也不是 Cloud Run 到 Neon 的完整搜尋延遲。評估工具不輸出向量或 access token，repo 中也沒有私人卡片內容。

## Chapter 8. 已驗證與下一步

目前已完成 #38 的設計文件、合成標記集、離線評分程式，以及由操作者回報的 Neon 權限／pgvector／合成計畫與 Vertex AI 測試。repo 內 5 個評分相關單元測試通過。`neondb_owner` 是文件記載的 migration 資料庫角色，且在測試 branch 可建立 extension；`app_runtime_limited` 沒有 database/schema `CREATE` 權限。正式 migration secret 當前的值沒有獨立讀回。

#39 接手向量表、內容 hash、寫入後補向量、匯入 backfill、失敗重試和重建。#40 接手搜尋 API、真正的 owner 安全整合測試及最終三表 `EXPLAIN`。#41 才能根據更接近使用情境的資料、成本與延遲決定是否繼續往 tutor 前進。不要把這份設計筆記寫成已上線功能或正式使用者成效。

## What we learned

1. **語意相似與授權是兩件事。** 向量只決定候選卡怎麼排序；身份、owner 和狀態必須由後端與 SQL 限制。
2. **外部 AI 呼叫不應決定已確認卡片是否存在。** 卡片先安全提交，失敗的向量可辨識、可補建、可重算。
3. **資料版本比單純「有沒有向量」更重要。** 模型版本、canonical text 與 hash 必須一致，否則會用舊內容搜尋新卡片。
4. **先量測，再加索引。** 小資料集的精確搜尋既簡單又保有完整召回；HNSW 應由最終查詢與真實延遲證據驅動。
5. **合成資料是起點，不是成效宣稱。** 1.0 的指標證明這組題目可以被找回，還不能證明對未見過的私人單字卡同樣準確。
